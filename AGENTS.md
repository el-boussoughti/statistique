# Project Notes

- **App :** gestion de quittances d'assurance — SPA statique (HTML/CSS/JS vanilla), export Excel/WhatsApp, stats.
- **Clés produit (RÈGLE IMPORTANTE) :** les personnes qui possèdent une clé secrète sont **VIP**. Leurs avantages : thème personnalisé, sticker + sono d'animation, accès à tous les boutons rapides et au menu clic droit. Sans clé = thème par défaut, 1ère rangée seule, pas de menu.
- **Sécurité des clés (token signé serveur) :** les avantages VIP ne dépendent **plus** d'un simple id en localStorage (spoofable). Architecture :
  - `js/app.js` garde les hash SHA-256 (clé en minuscules) **pour l'UX uniquement** (auto-remplissage opérateur, thème, animation). Ne jamais remettre les clés en clair.
  - `lib/auth.js` (fonctions Vercel) est la **seule autorité** : `/api/verify` valide la clé (SHA-256) et délivre un **token HMAC-SHA256** (`{iat, exp, id}.<sig>`), `/api/check` le revalide au chargement. Le secret HMAC n'existe que serveur (`QUITTANCE_SECRET`, ≥16 caractères, obligatoire ; `QUITTANCE_TOKEN_TTL_DAYS`, défaut 30).
  - Client : `applyKeyState` n'accorde le VIP persistant que si un token valide a été obtenu. `restoreKeyState()` (au chargement) appelle `/api/check` ; `verifyKeyAsync()` (saisie clé dans « Nouvelle session ») appelle `/api/verify` et stocke le token dans `quittance_secret_token`. Sans token → `applyKeyState(-1)` (fail-closed, `no-key` par défaut dans `<body>`). Hors-ligne → pas de VIP.
  - **MAINTENANCE : ajouter/éditer une clé dans les DEUX fichiers** (`js/app.js` + `lib/auth.js`) — sinon l'UX et l'autorité divergent.
  - Résidus assumés : un utilisateur déterminé peut toujours patcher en console/session (limite client, impossible à fixer sans backend total), et copier le token réel d'une machine VIP (mitigé par TTL + re-vérification). Rate-limit in-memory par IP sur `/api/verify` (15/min, par instance).
  - **Tester/vivifier localement :** `npx vercel dev` (env `QUITTANCE_SECRET`) pour avoir les fonctions `api/` en local. Sans backend (serveur statique seul ou `file://`), la clé est refusée — c'est voulu (fail-closed). Si `/api/verify` répond 500 → `QUITTANCE_SECRET` manquant ou trop court. Diagnostic : `/api/health` renvoie `{ok, secretConfigured, secretLength}` (sans fuiter le secret).
- **Thèmes :** `css/style.css` (`:root[data-keytheme="…"]`, 3 variantes clair/sombre/auto + `--accent-text`). Nouvelle clé = hash dans `app.js` + éventuel bloc CSS.
- **Déploiement :** Vercel, statique. Les assets sont versionnés (`?v=`) et servis avec `Cache-Control: no-store/must-revalidate` via `vercel.json` — toujours hard-refresh après un push.
- **Nouvelle session :** « Tout effacer » ouvre le modal avec tous les champs **vides sauf la date** (aujourdʼhui). Champs **obligatoires** pour ajouter une quittance : Opérateur, Service, Date, Registre N°, **Quittances N° Du**, N° quittance (`missingRequiredField` dans `js/app.js`, appelé par `addEntry`/`addQuickEntry`).
- **Tiroirs VIP :** badge VIP visible en haut quand une clé est active (`body:not(.no-key)`).
- **Export Excel protégé :** le fichier `.xlsx` exporté est protégé par mot de passe (`EXPORT_PASSWORD` dans `js/app.js`, par défaut `CHR2026`). Toutes les cellules sont **verrouillées** et la feuille est protégée avec `selectLockedCells:false` → impossibilité de modifier, formater et **copier/cssélectionner** (ExcelJS `ws.protect()`, sans mot de passe pour déprotéger). Limite Excel : seule la protection par feuille/mot de passe legacy est supportée (pas de chiffrement fichier ni de protection de classeur dans ExcelJS).
- **Auto totale (VIP uniquement) :** bouton « Auto totale » dans le `card-header` de la liste, visible **uniquement en plein écran** (`body:not(.no-key) .content-grid.list-fullscreen .auto-totale-wrap`). Il ouvre un **popover** avec 5 pastilles (1-5) pour choisir les quittances restantes de la 1ʳᵉ page + « Activer » / « Désactiver » (état via `data-active` sur le wrap). La sélection est stockée dans `autoTotaleSel` (js/ui.js). Active un total après chaque page du registre. Les lignes `page-total-row` ne s'affichent qu'en **plein écran** (`showAll`) ; hors plein écran, pagination normale. Les pages suivent l'**ordre physique du registre** = N° croissants (page 1 = X restantes 1-5 réglables, puis groupes de 5). Quand Auto totale est actif **en plein écran** : la liste est **forcée en N° croissants**, tout autre tri est bloqué (`sortEntries`/`resetSort` refusent avec un toast, `sort-locked` en CSS, flèches masquées) et la **barre de recherche est masquée** (`content-grid.auto-totale-on .search-container`). Hors plein écran : tri et recherche normaux. ANNUL comptés comme 0. Totaux **cumulés** : page 1 = somme de ses quittances, page N = somme de ses quittances + total de la page précédente (`pRunning` dans `js/render.js`). État persisté dans `quittance_auto_totale` (`js/app.js`), rendu dans `js/render.js` (Map « dernier N° de page → {pnum, sum} »). Bump toujours `?v=` dans `index.html` après modification.
- **Azkar AFK :** popup Azkar s'affiche après 60 s d'inactivité (aucune action clavier/souris), reste tant qu'on est inactif, se ferme **1 s** après la première activité (ou via bouton X). Rafraîchit un autre azkar aléatoire à chaque nouvelle inactivité. 14 azkar (arabe seul, sans traduction). Popup **centré + overlay sombre**. Code dans `js/azkar.js`, styles dans `css/style.css`, markup dans `index.html` (`#azkar-dialog`).
- **Le Gardien (« Guardian », vérification des prix) :** bouton « Gardien » dans le `card-header` de la liste (`#guardian-btn`, `js/guardian.js`), **VIP uniquement** (`body.no-key #guardian-btn{display:none}` + `guardianInit`/`guardianRefreshButton` renvoient tôt si `.no-key`). Sa couleur dépend de l'état : **thème** si tout est OK, **orange** si au moins une alerte, **rouge** si au moins une erreur, rafraîchie à chaque `render()` (`guardianRefreshButton` appelée depuis `js/render.js`). Classement selon `GUARDIAN_RULES` (`js/guardian.js`) :
  - `fixed` (C1=40, C2=60, CML=100, CMD=40) → valeur exacte : **correct** sinon **mistake**.
  - `multiple` (ACC base 80) → multiples de la base (≥1) : **correct** sinon **mistake** (0 exclu).
  - `combo` (RX : 112.5,120,30,90,75 ; LABO : 22.5,30,52.5,75,37.5,60,150,187.5 ; HOSP : 400,150) → somme de multiples des valeurs connues (algo `_isCombo`, mémoïsé, max 8 éléments) : **correct** ; sinon si valeur jamais validée à la main → **warning**.
  - `multiple` (ACC base 80) et `fixed` peuvent cohabiter pour un type sous forme de **tableau de règles alternatives** (un type est correct si ≥1 règle est respectée). Ex. `EXP` : `[{fixed:50}, {multiple base 700}, {multiple base 2000}, {combo values:[165,150,200,225,300,337,120,450]}]` — 50 sans double/combinaison, 700/2000 en multiples seuls, et combos/multiples du dernier set. La présence d'une règle `combo` rend le type « ouvert » : valeur hors règles = **warning** (sauf `fixed`/`multiple` seul = **mistake**). Un combo vide (montant 0) n'est jamais accepté (`_matchRule` exige `m>0`).
  - `free` (ANNUL + types inconnus) → toujours **correct**.
  - **Anti-explosion performance :** `_isCombo` (js/guardian.js) est borné — `_comboMaxMult=40`, `_comboWorkLimit=300000`, flag `_comboCapHit` (purge le cache `_comboCache` quand la limite est atteinte). `classifyEntry` renvoie **mistake** pour montants non finis (NaN/Infinity) → aucune boucle infinie. Validation : LABO 5 000 000 → <50 ms, 10 000 entrées → <10 ms.
  - Le modal `#guardian-modal` a **3 onglets** (Correct/Avertissement/Erreur) avec compteurs, en-tête (icône + titre + bouton X), pied de page (nb de quittances analysées + total dh), lignes avec icône d'état, raison du verdict et actions. Onglet Avertissement : boutons « C'est correct » (ajoute la valeur à `GUARDIAN_VERIFIED`, persisté dans `quittance_guardian_verified`) ou « Corriger… ». Onglet Erreur : bouton « Corriger… ». « Corriger… » ouvre un **modal dédié** `#guardian-fix-modal` (au-dessus, `z-index:10300`) : pastilles N°/type/ancienne valeur → nouvelle valeur, erreurs inline, aperçu live (`#fix-chip-new`), Entrée=valider, Échap=annuler → `saveState()` + `render()`. Échap ferme aussi le modal principal. Toujours bump `?v=` après modification.
- **Durcissement sécurité & données (appliqué) :**
  - `escHtml()` dans `js/app.js` → toutes les interpolations HTML de type/montant/raison passent par `escHtml` dans `js/render.js` (badge type + cartes breakdown) et `js/guardian.js` (`_guardianRow` + chips du fix-modal) → plus de XSS par type `<b>x</b>`.
  - `_sanitizeEntries()` (js/app.js) : filtre/normalise les entrées au chargement (n entier ≥1, type string non-vide, montant fini >0), tri desc. `loadState` est durci : JSON corrompu → `entries=[]`, `nextN` auto-réparé s'il est < maxN+1.
  - `nextN` (addEntry/confirmation) ne recule jamais : `Math.max(nextN||0, entries[0].n+1)`.
  - Tri par colonne N° : premier clic = **desc** (ordre registre, `sortAsc = (col !== 'n')`), second = asc.
- **Tests :** suite Node complète sans dépendances (`tests/suite.js`, DOM + localStorage stubbés) — `npm test`. **199 assertions, viser 0 échec.** Couvre : XSS, règles Gardien, fix-modal, calculs/stats, auto-totale, tri/pagination, nouvelle session, stockage corrompu (NaN/Infinity/JSON invalide), grandes données (10 000), export Excel protégé, azkar, token HMAC serveur (`lib/auth.js` : sign/verify/tamper/expiry/rate-limit). Après toute modif de js/logique → relancer `npm test` + bump `?v=`. Un échec de tri/bootstrap avec des valeurs bizarres (« got 500 ») est souvent un artefact du stub (extraction regex des N°) et non un bug de l'app.
